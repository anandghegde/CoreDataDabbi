## 1. How to read this plan

- Milestones M0–M6 are the PRD's (§12). Each is split into work packages `Mx-nn` with tasks, the PRD IDs they satisfy, a size, and dependencies.
- **Sizes** are ideal engineering days for one experienced macOS developer: **S** ≤ 2 · **M** 3–5 · **L** 6–10 · **XL** 11–15. They are for ordering and scoping, not commitments; recalibrate after M0.
- Module and type names refer to the architecture document.
- Every WP ships with tests and, where it adds public `DabbiKit` API, DocC comments. Definition of done is in §11.

## 3. Critical path

```mermaid
graph LR
  M0["M0 Foundations<br/>engine reads every fixture"] --> M1["M1 Viewer<br/>daily-drivable"]
  M1 --> M2["M2 Query + Track"]
  M2 --> MVP(["MVP cut"])
  M2 --> M3["M3 Edit + Exchange<br/>+ snapshot/restore"]
  M3 --> M4["M4 Parity polish → 1.0"]
  M4 --> M5["M5 → 1.1"]
  M4 --> M6["M6 → 1.2"]
```

Within the path, the items that gate everything else: `ModelLoader` + sanitiser (M0-04) → `StoreSession` paging (M0-06, M1-04) → grid (M1-05) → tracker (M2-06…09). Content decoders, locator, diagrams, exchange and diagnostics are off the critical path and are the natural places for parallel contributors.

Rough duration for one full-time developer: **M0 5–7 wk · M1 9–12 · M2 9–12 · M3 10–13 · M4 10–14 · M5 7–9 · M6 8–10.** MVP (M0 + M1 + tracker half of M2) ≈ 20–26 weeks; 1.0 ≈ 43–58 weeks. Part-time or multi-contributor work scales accordingly.

**Progress (2026-09-23).** M2 is complete: M2-01 through M2-13 are in, M2-12 (auto-repair) last. - **M2-01** done — `DabbiQuery` now holds the predicate core described in Architecture §6.5:
  - `PredicateAST` (`PredicateAST.swift`) — the one source of truth: `Codable`, `Sendable`, `Hashable`, with `PredicateComparison`, `PredicateExpression`, `PredicateLiteral`, `PredicateOperator`, `PredicateModifier` and `PredicateOptions` beneath it. `NONE` is stored as `NOT(ANY …)`, `TRUEPREDICATE`/`FALSEPREDICATE` get their own cases, and anything the walk cannot name survives as `.custom(text)` rather than being lost.
  - Conversion (`PredicateConversion.swift`) — text → AST goes through `PredicateGuard.parse`, and AST → `NSPredicate` re-runs `PredicateGuard.check`, because an AST can also arrive from a project file somebody edited by hand (`PredicateGuard.check` is public now for that). `PredicateSource` stays the stored form everywhere and `PredicateSource.ast()` is the way in. 23 predicate shapes round-trip losslessly in the tests, `SUBQUERY(…).@count` among them — that one needed the key-path *specifier* expression type, which has raw value 10 and no `NSExpression.ExpressionType` case.
  - Key paths (`KeyPathResolution.swift`) — `KeyPathResolver` walks a path component by component against the `ModelDescription`, through to-one and to-many relationships, `@count` and the other collection operators, and composite elements (S3's KVC question, from the model's side). A failure carries the resolved prefix, the component that failed and up to three "did you mean" names by edit distance. Collection-ness is threaded along the walk rather than read off the last component, so `books.title` is a collection and `books.@count` is not.
  - Validation (`PredicateValidator.swift`) — diagnostics with severities: a bare to-many key path without `ANY`/`ALL` is an error (the SQLite store refuses it) and is offered both spellings; `@sum` and friends are a warning (the store only does `@count`); `IN`/`BETWEEN` against a single value, `BETWEEN` without exactly two, and a comparison against a fetched property are errors; transformable comparisons, type-group mismatches, `[cd]` on a non-string operator and `.custom` nodes are warnings. It also reports `missingKeyPaths` for PRD-5's badge and the `$NAME` substitution variables M2-05 will prompt for — a `SUBQUERY` iterator is bound to its collection's entity and is not one of them.
  - Builder support (`PredicateBuilderSupport.swift`) — `isBuilderRepresentable` and `builderObstacles` decide what M2-03 can show and say why, in words, when it cannot; `normalisedForBuilder()` puts the key path on the left, and only when the operator has a reverse, because turning `"Swift" BEGINSWITH name` around would ask a different question.
  - `dabbi query --where` validates against the model before fetching, so a mistyped key path is a sentence on stderr instead of an exception from inside Core Data.
- **M2-02** done — the predicate bar, between the breadcrumb and the grid (Architecture §8):
  - Completion (`PredicateCompletion.swift`, `DabbiQuery`) — half a predicate rarely parses, so `PredicateCompleter` never goes through `NSPredicate`: it lexes the text up to the caret, resolves the partial key path in front of it against the model, and offers what can follow — the entity's attributes and relationships, `author.na` continuing as an Author's properties, the operators the type on the left allows, `[cd]`, `ANY`/`ALL`, `@count`, `AND`/`OR`/`NOT`, `nil`, `TRUE`/`FALSE`. Inside a string, after a number or behind a key path the model does not have, it offers nothing rather than guessing. Ranges are UTF-16 offsets, which is what AppKit's text views count in.
  - The bar (`App/CoreDataDabbi/Query/`) — `PredicateBarModel` checks what is typed on every keystroke through `PredicateValidator` and says what is wrong in a line under the field; `canApply` is false while it is wrong, so nothing that failed validation reaches a fetch. Return applies, Escape puts the applied predicate back or hands the keyboard to the rows, ⌥⌘F reaches the field from anywhere in the window (§8.3).
  - `PredicateTextField` gives the field its own field editor: `rangeForUserCompletion` returns the range the completer asked for, so `[cd`, `@cou` and `first_na` are replaced whole where a standard editor stops at the punctuation, and smart quotes, dash substitution and autocorrect are off — each of them would silently change what the predicate says.
  - The applied predicate is the entity's, kept in `EntityLayout.filter` next to its columns and its sort, so it is written to `project.json` and comes back with the window; the grid re-fetches through the same observation path as a sort change.
- **M2-06** done — `DabbiTracking` now holds the head of the tracker chain (Architecture §6.6):
  - `StoreWatcher` (`StoreWatcher.swift`) — an actor handing out `AsyncStream<StoreCommit>`. The first subscriber opens the gate connection and arms the watching, the last stream to finish stops it, and `stop()` followed by `commits()` starts it again, which is what Play/Stop/Play (TRK-1) will need. Three ways of noticing, cheapest first: a `DispatchSource` on the store, its `-wal` and its `-shm`; one FSEvents stream on the folder, for a file replaced rather than written; and an optional poll (2 s by default) as insurance on a file system that reports nothing. All of them settle through one 150 ms debounce, so a burst of transactions costs one gate read.
  - The gate is `PRAGMA data_version` on a long-lived read-only connection that never holds a transaction open. It moves only when *another* connection commits, so the app opening the store, a checkpoint, or an `-shm` rebuilt by a reader reach no subscriber — and nothing the watcher does pins the WAL or stops the inspected app from checkpointing.
  - `FileEventSource` wraps a vnode source as `.changed`/`.vanished`. `DirectoryWatcher` moved from `DabbiLocator` down to `DabbiBase`, so the simulator index (§6.7) and the watcher can both use it without one sibling module importing another.
  - The store *file* being replaced is `.storeReplaced`, not a commit: every primary key and prior value cached about the old file is about a file that no longer exists, which M2-07…09 will have to act on. Any of the three files changing identity also closes and reopens the gate connection.
  - Corrected here: §6.6 said the companion files are recreated at a checkpoint, so a restart would force a re-arm. Measured, Core Data keeps them — the `-wal` is truncated in place and both keep their inodes across a restart — so re-arming is for reinstalls and restores instead. Deleting them under a live reader turned out to make the store unopenable for the app itself (`SQLITE_IOERR_VNODE`), which is the other reason the connection is dropped as soon as the files change (Architecture App. D).
  - `StoreWatcherTests` — twelve tests against a real Core Data writer: the `data_version` canary, noticing a commit inside the budget, saying nothing when nothing committed, coalescing a burst, the poll not double-reporting, an app restart, the companions replaced, the store replaced, and the lifecycle.
- **M2-07** done — the scan half of the tracker, the stage that turns "something committed" into "these rows" (Architecture §6.6):
  - `ChangeScanner` (`ChangeScanner.swift`) — an actor on its own read-only connection. It keeps, per table, the `Z_PK`, `Z_ENT` and `Z_OPT` of every row in scope and diffs two of those: a key that went away was deleted, one that appeared was inserted, one whose save counter moved was saved over (Architecture App. A). No row *values* are held, so it never has to decide whether a value it cannot decode changed. `prime()` reads the baseline without reporting it — the rows already in a store are not news — and `reset()` drops both the baseline and the connection, which is what a `.storeReplaced` commit from M2-06 calls for.
  - One transaction. Every tracked table and join table is read inside a single read transaction, so a save that touched three entities is seen whole; table-by-table reads would show the halves of one save as two changes, in an order decided by nothing but timing.
  - `TableSnapshot`/`JoinSnapshot` (`TableSnapshot.swift`) — three parallel arrays rather than an array of structs, sorted by `Z_PK`, which costs nothing to ask for because that *is* the order SQLite walks the table in. The diff is the merge half of a merge sort over the two sorted key arrays. Join tables ride along with the order column, because a reorder of an ordered many-to-many changes `Z_FOK_…` and nothing else, and a tracker comparing only pairs would say nothing happened.
  - `ScanPlan` (`ScanPlan.swift`) — made once per connection from the model, the `SchemaMap` and the database's own `PRAGMA table_info`: which tables to read, which columns they really have, which `Z_ENT` number means which entity, and which join table belongs to which relationship (one direction of each, so a many-to-many is not read twice). What it cannot do becomes a `ScanLimitation` — a missing or unverified table, no `Z_OPT` (inserts and deletes still work; updates are lost), no `Z_ENT`, a many-to-many whose join table is not where convention says — and `RawChangeSet.isReducedFidelity` is what the tracking UI will label a session with. An entity number no `Z_PRIMARYKEY` row accounts for is found while diffing rather than while planning, because a number only turns up when a row carries it.
  - `TrackingScope` (`TrackingScope.swift`) — `.allEntities` or a list of names; naming `Person` also watches `Employee` and `Manager`, since a sub-entity's rows live in the root's table and the question "has a Person changed" is about them too. Abstract entities resolve to their concrete children and nothing else.
  - `RawChangeSet` (`RawChanges.swift`) — `RowID` (entity + primary key), not `ObjectRef`: nothing here has fetched an object, and a URI would be claiming more than a key read knows. - **M2-08** done — persistent history, read both ways, as *enrichment over the scan* (Architecture §6.6, TRK-10). M2-07 answers which rows changed; this package answers who changed them, when, and — for a row nobody had read — which fields.
  - **The design decision, and it is the whole package.** The plan's phrase was "history-first strategy". It is not built that way, and the reason is a fact about stores rather than a preference: `NSPersistentHistoryTrackingKey` is per *open*, not per file, so a store can carry `ATRANSACTION` and `ACHANGE` and still be written by a process that saves with tracking off — those saves reach the file and never reach history. A history-first tracker would miss them in silence, which is exactly what ADR-17 forbids. So `ChangeScanner` stays the one answer to *which* rows changed, history is layered over it, and a scanned row history cannot account for is reported as a `historyIncomplete` limitation rather than hidden. The cost of being wrong the other way is only a missing author.
  - `HistoryToken`, `HistoryTransaction`, `HistoryChange`, `HistoryInfo` (`DabbiBase/History.swift`) — the `Sendable` values both readers produce. A token carries `ATRANSACTION.Z_PK` *and* the archived `NSPersistentHistoryToken`, so either reader can carry on from the other's token; that matters at the one moment the strategy can change, a store that starts out readable through the public API and stops being so. `HistoryChange.updatedProperties` is `Set<String>?` where `nil` is *not known*, never *none* (ADR-17).
  - `StoreSession.currentHistoryToken()`, `historyTransactions(after:limit:)`, `history(of:limit:)` (`DabbiStore/StoreHistory.swift`) — the public-API half. Three things had to be worked around: Core Data ignores `fetchLimit` on a history fetch, so the limit is applied in memory and says so; `transactionNumber` is not a queryable key path, so the newest transaction number comes from `SELECT MAX(Z_PK) FROM ATRANSACTION` through the SQLite reader; and one object's timeline is scoped by `changedObjectID` on the *change* entity rather than with `.changesOnly`, which drops the transaction back-reference and with it the author and the timestamp — the whole reason a timeline is worth showing. Nothing Core Data owns leaves a `perform` (ADR-02, ADR-03).
  - `RawHistoryReader` (`DabbiTracking/RawHistoryReader.swift`) — the fallback, reading `ATRANSACTION`, `ACHANGE` and `ATRANSACTIONSTRING` as tables through the read-only SQLite connection. It probes the columns it finds rather than assuming them: the four interned string fields are each `LEFT JOIN`ed to `ATRANSACTIONSTRING`, falling back to the plain `VARCHAR` twin beside them and then to nothing, and `ZTOMBSTONE<n>` is followed as far as the table goes. Both queries run inside one read transaction, so a save landing mid-read cannot produce a transaction whose changes are half old and half new.
  - **The format fact this package had to establish** (Architecture App. A): `ACHANGE.ZCOLUMNS` is a big-endian bitmap whose bit *n*, counted from the most significant bit of the first byte, is the *n*th of the row's own entity's non-transient properties — **attributes and relationships in one list, sorted by name**. Not attributes first and relationships after, which is what it was first built as and which happens to agree on `Folder` and disagree on `Note`; not the entity table's column order either, which for `ZNOTE` is `ZPINNED, ZFOLDER, ZMODIFIEDAT, ZBODY, ZTITLE`. A sub-entity numbers its own list, not its root's. `ZTOMBSTONE<n>` follows the same name order over the attributes marked `preservesValueInHistoryOnDeletion`. A bit past the end of the list makes the whole bitmap unknown rather than a partial answer.
  - `HistoryReaders.open(for:preferring:)` — the choice between the two is *proved*, not assumed: each candidate is asked for the store's current token and one that cannot answer is closed and passed over. That is what makes the fallback worth having, because the failure it guards against shows up exactly there, at the first question.
  - `HistoryDigest` (`TrackerHistory.swift`) — a batch's transactions folded row by row, because the scan reports the *net* change to a row over a whole batch and the enrichment has to be about the same thing. Attribution comes from the last transaction that touched the row, with `transactionCount` saying how many saves stand behind that one name; property names are the union across the batch, and one transaction that will not say makes the union unknown rather than partial.
  - What reaches the UI: `ChangeEvent.history` (author, context, process, save time, transaction number), `ChangeEvent.beforeIsTombstone`, `ChangeBatch.authors` and `ChangeBatch.savedAt`. Two enrichments change what an event *says* rather than just labelling it, and both fill gaps M2-09 left open by design: a row nobody had read gets its changed property names from history — `before` stays `nil`, because naming a field is not knowing what it was — and a row deleted before anybody read it gets its preserved attributes as `before`, marked as a tombstone so nothing mistakes it for something somebody saw. Where a real diff exists it wins: history says what a save *wrote*, the diff says what *changed*, and writing a field the value it already held is not a change.
  - Ordering, which is the one race here: history is read *before* the scan, because the reverse would advance the token past saves the batch does not report and lose their attribution for good. The token is committed only after the scan succeeds. A save landing between the two is reported by the scan and unaccounted for by history — which is a `historyIncomplete` limitation, one per entity, entity names only (§10).
  - Kept quiet on purpose: the limitation is raised only when enrichment is on, the store actually carries history tables, and the batch reports rows. An ordinary store with no history is never `isReducedFidelity` for this reason, or the flag would mean nothing.

- **M2-09** done — the second half of the tracker: the stage that turns "these rows changed" into "this is what changed about them" (Architecture §6.6). With M2-06 and M2-07 in front of it, the engine now does end to end what M2-10 has to draw.
  - `ChangeTracker` (`ChangeTracker.swift`) — the actor that owns the chain: a `StoreWatcher` commit wakes a `ChangeScanner`, the keys it reports are materialised through the session's tracking context, the readings are diffed against what was held, and one `ChangeBatch` per commit goes to every subscriber and into the `VersionLog`. `start(_:)` is `async throws` and not cheap on purpose — it reads a baseline, primes values and may copy the store — and `stop()` lets go of everything about the file while keeping the log, because the user is still reading it. The drain loop is deliberately reentrant: a commit landing mid-scan raises the pending count and is picked up by the loop in flight rather than starting a second scan on the same connection. `pause()`/`resume()` (TRK-9) keep counting commits and report their *net* difference — a row inserted and deleted again while paused is not news — and the batch says how many commits it stands for, so a log that coalesces never pretends it did not.
  - Materialising, in `DabbiStore` (`StoreSession.reference(entity:pk:)`, `references(_:limit:)`, `objects(_:matching:batchSize:)`): references are made from a key and an entity name with nothing read, because the scan has the keys already and asking the store to confirm each one would undo the point of reading them from SQLite. Objects come back by each row's *own* entity's layout — a Manager's columns, not the Party table's — in batches of 500, mixed entities in one call, to-many relationships as counts gathered for the whole batch in one grouped fetch rather than one fetch per row. A reference with no row is absent from the answer rather than an error: that is how the tracker learns a row it was told about has gone again.
  - `FieldDiff` (`FieldDiff.swift`) — compares two readings by property **name**, never by position, and only over the properties both sides carry. The before may have come from a grid page whose columns are the union of an entity and its sub-entities, or from one fetched lazily with three columns of twenty; comparing `values[i]` to `values[i]` across those would report changes that did not happen. A property only one side has is not a change but a difference in what was read — which is what makes the external-blob case below honest rather than wrong.
  - `PriorValues` (`PriorValues.swift`) — values and view membership, kept together because they are learnt together. Values are capped (default 100k rows, oldest arrivals first) and come from three places: priming, materialising an earlier change, and `ChangeTracker.remember(_:)`, which the grid feeds for free with the rows the user is already looking at. Membership is the only way to tell *entered* from *left*, since a predicate can only answer "does it match now". Neither is ever guessed: no reading gives a `nil` before and a `nil` `changedKeys` — *changed, prior value unknown* — and unknown membership gives no transition at all.
  - Priming — entities up to `primeUpTo` (50k rows) are read whole; a larger one is not read at all, but its membership still is when there is a predicate, because identities are cheap. A view bigger than the threshold leaves `membershipIsComplete` false, so absence means unknown rather than non-member. Nothing here is fatal: an entity that cannot be primed is one whose rows start out unknown, which the events about them say.
  - TRK-7 — the predicate half of tracking, which M2-07 deliberately left alone because the scan reads no values. It is `TrackingScope.predicate`, evaluated per row while materialising (`matchesPredicate`), compared against primed membership, and reported as `.entered`/`.left`. Changes to rows outside the view are not reported at all; an entity that cannot answer the predicate leaves it unknown rather than "no".
  - TRK-9 link changes — a join-table link that moved arrives twice over, and both are wanted: the scan names the link and its position, and the reading of the row shows its to-many *count* change, so the grid's own columns show it without the UI joining anything.
  - `VersionLog` (`VersionLog.swift`) — append-only, numbered from one, in memory to the cap (10k) and spilling older versions to a temp SQLite database of our own, values and diffs and all. Reads that cross the boundary gather from both sides in one run: the recent list, one object's history, and a page forwards from a cursor, which is how an export walks it (TRK-5). The spill holds row values, so it is deleted with the log. Without a spill it drops and counts what it dropped, because a log that quietly forgets is worse than one that admits it; `clear()` (TRK-9) empties the contents and not the counter, so a version the user has seen cannot come back under a number they have also seen.

Comparing that against the live store reported an untouched blob as emptied; those attributes are now left out of a deep reading entirely, which makes the field unknown — true — instead of changed. - **M3-05** done — validation UX (EDT-2, Architecture §6.4).
  - `ValidationIssue` (`DabbiBase`): the object (`PendingObjectID`), the property (`nil` for the object as a whole), the `rule` (`required`, `tooShort`/`tooLong`, `belowMinimum`/`aboveMaximum`, `tooEarly`/`tooLate`, `invalidDate`, `patternMismatch`, `invalidURI`, `tooFewObjects`/`tooManyObjects`, `deleteDenied`, `notUnique`, `other`), the model's figure as it states it (`limit`), a relationship's `count` where that is what is wrong, and an English sentence — “Must be at least 1 character long.” Never the value.
  - `ValidationTranslator` (`DabbiStore`) turns Core Data's validation errors into issues, `NSDetailedErrorsKey` unfolded. A model made in Xcode names each rule by its error code; one built in code may give a rule a message of its own, and Core Data then reports the generic code with the predicate that failed (`NSValidationPredicateErrorKey`) — the translator reads the predicate's shape (`length >= n`, `SELF <= max`, `SELF MATCHES p`) for the rule and its figure, and falls back to the model's `ValidationFacets` when the error carries neither. Every answer about what is staged — each edit, undo, redo, `pendingChanges()` — runs `validateForInsert`/`Update`/`Delete` over the changed objects and carries the result as `PendingChanges.issues`. Validating registers nothing with the undo manager. A refused commit's diagnosis is the same issues, one line each (`Sample#3 · name: …`), replacing M3-04's own wording. Uniqueness constraints are left to the commit: SQLite checks them, and only a save asks it.
  - `StoreSession.deletePreview(of:)` → `DeletePreview`: what Cascade takes along, what Nullify unlinks, what is left *dangling* — No Action, or a relationship with no inverse, found by a fetch, since Core Data cannot follow one back — and the issues the commit would meet: Deny rules with objects still behind them, and rules of the objects that stay which unlinking breaks (a required to-one emptied, a to-many left under its minimum). It follows the rules by reading, not by staging and undoing: a cancelled preview must leave the redo stack alone. Its Deny counts only objects that stay; the staged delete's own validation is what decides.
  - App — the Pending Changes panel lists each object's issues under its fields and counts them in its header; the inspector shows an issue under the field it concerns (object-level ones under the header) and now re-reads the object whenever what is staged changes, so its values and its issues agree; a grid cell whose staged value breaks a rule has a warning symbol, and the rule as its tooltip and accessibility help. Nothing is told by colour alone (§8.4). *Delete Rows* asks first when the preview is more than the rows — a cascade, dangling references, or a commit that would be refused — and says which; a plain delete, Nullify included, is staged without asking. The question is part of the edit's turn in `EditingSession`, so nothing staged after it overtakes it. Commit stays enabled with issues outstanding: the commit is what decides, and it explains itself when it refuses.
  - Tests — engine: `ValidationTests` (11: rules broken by an edit, a missing required value, inserted objects, issues following undo and redo, a refused commit listing the same issues, a denied delete, messages; previews that stage nothing and keep the redo stack, Nullify alone being plain, a cascade and the denials it meets, one-way references found dangling). App: `EditingSessionTests` +3 (issues by object and field; a delete that reaches further is asked about, declined and accepted; a plain one is not), `GridCellTests` +1.
  - Written in a Linux container without Xcode. The new engine files and the engine tests were typechecked in Swift 6 language mode against stand-ins for Core Data's API, `EditingSession` against stand-ins for `DabbiKit` and `UndoManager`, the messages the tests expect were run, the whole tree linted with swift-format 6.2.3 (which passes the existing tree unchanged) and the String Catalog entries written in `xcstringstool`'s own format. Neither suite has been run on a Mac yet; CI is the first to.
  - Left for later: inline editing and the detail window are M3-06, where these issues sit beside the fields being typed into; a pre-check of uniqueness constraints before the commit; localising the engine's sentences (front ends can render `rule`, `limit` and `count` themselves).

- **M3-06** in progress — editing surfaces (EDT-3, BRW-9). Taken in slices, each merged on its own: inspector editing, inline grid editing, New Object with inserted objects inspectable, then the detail window and its relationship pane.
  - Slice 1 — inspector editing. `ValueText` (`DabbiModel`) is the one place text becomes an attribute's value and back: numbers as stored (no grouping, a full stop), dates as ISO 8601 with the project's offset and fractions only when there are any, `yyyy-MM-dd[ HH:mm[:ss]]` read in the project's time zone, empty text as no value for every type but String. What it writes reads back as the same value for every editable type; what it refuses is explained without repeating what was typed. Import's coercion (M3-09) is to use it. In the Details tab each field is a `FieldRow`: when the store is open for editing, the pencil, *Edit Value* in the context menu or VoiceOver's action open a text field, Return (or leaving the field) stages what was typed through `EditingSession.setValue`, Escape leaves it, and text that is not a value of the type stays with the reason under it. *Set to Nil* for optional attributes. Rows are rebuilt per object, so a half-typed field never carries over to the next one.
  - Tests — engine: `ValueTextTests` (7; they also run on Linux, being platform-neutral). App: `EditingSessionTests` +2 (the inspector stages what is typed and explains what it cannot read; a read-only store offers nothing to edit).
  - Next: inline grid editing through the same `ValueText`; New Object, which needs the inspector to read an object that has no key yet; to-one and to-many editing, which need link/unlink in the engine and an object picker.

## 11. Working agreements

**Definition of done (every WP):** tests at the right tier pass in CI · no new strict-concurrency warnings · public engine API documented · user-visible strings in the String Catalog · accessibility labels for new controls · no row data in logs · PRD IDs referenced in the PR · ADR added or amended if a decision changed.

**Branching and PRs:** trunk-based, short-lived branches, squash merge, DCO sign-off (`git commit -s`), one WP may span several PRs. Labels: `prd:<ID>`, `milestone:Mx`, `area:<target>`, `good first issue` on plug-point work (decoders, exporters, Doctor checks, diagram emitters).

**Clean-room rule:** behaviour comes only from public docs and Apple frameworks; PR template has a checkbox affirming it.

**Performance regressions** fail the run when a baseline on the 1M-row fixture regresses past its budget — `Scripts/perf.sh` for the engine, `Scripts/perf.sh app` for the grid, both asserted by the tests themselves. As of M1 they are run by hand, not in CI: the fixture takes minutes to generate, and a frame budget measured on a shared runner would be noise. A run before a release, and after anything that touches paging or the grid.
